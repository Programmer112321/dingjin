Pre-Processing Airborne LiDAR Data: lidR vs lasR Side-by-Side

LiDAR
3DEP
Pre-processing

Tutorial
A complete LiDAR pre-processing pipeline — from raw LAZ tiles to clean, normalized, metric-ready point clouds — with every stage shown in both lidR and lasR, plus pros/cons and decimation and noise-removal method comparisons.
Author

Dingjin Chu

Published

February 15, 2026

Airborne LiDAR point clouds are rarely analysis-ready out of the box. Raw tiles from 3DEP, NEON AOP, or proprietary acquisitions often carry noise, inconsistent densities across acquisition campaigns, and missing height normalization. This post documents a reproducible pipeline in R covering every stage from raw LAS/LAZ ingestion to a clean, normalized, decimated cloud — shown in parallel in both lidR and lasR.

lidR vs lasR — Core Philosophy

lidR lasR
Processing model Loads tiles into R LAS objects, one chunk at a time Streaming C++ pipeline; tiles never fully loaded into R memory
API style Function calls on LAS/LAScatalog objects Stage composition with +, executed via exec()
Speed Single-threaded R loops; C++ for some algorithms Fully multi-threaded C++ — 5–10× faster on large datasets
Memory footprint One chunk in RAM at a time; scales with chunk size Constant regardless of file size
Interactivity Easy mid-pipeline inspection and visualization Batch-only; harder to inspect intermediate states
Best for Exploration, small–medium datasets, learning Production pipelines, large tiles, HPC

Part 1: Pre-Processing Pipeline — Stage by Stage

Stage 1 — Input & Catalog / Pipeline Setup

  • lidR
  • lasR
library(lidR)

# Build catalog from all tiles in a directory
ctg <- readLAScatalog("path/to/las_folder/")

# Drop pre-labeled noise at catalog level (Class 7 = low, 18 = high noise)
opt_filter(ctg)       <- "-drop_class 7 18"

# Set chunk buffer (required for SOR neighborhood at tile edges)
opt_chunk_buffer(ctg) <- 10        # metres

# Control chunk size if memory is constrained
opt_chunk_size(ctg)   <- 500       # 500 × 500 m chunks

# Inspect point density and tile coverage
plot(ctg, mapview = TRUE)
summary(ctg)
library(lasR)

# In lasR there is no catalog object.
# The folder path is passed directly to exec().
# Filtering, buffering, and chunk size are set in exec() or on the reader stage.

read_stage <- reader_las(filter = "-drop_class 7 18")

# Buffer and chunk size are arguments to exec()
# (set once for the entire pipeline)
NoteStage 1 — Pros & Cons
lidR lasR
Pros LAScatalog gives a visual tile map; summary() reports per-tile density and coverage; easy to spot problematic tiles before running anything No catalog setup needed — folder path goes straight to exec(); less boilerplate; buffer/chunk settings in one place
Cons Catalog creation scans all file headers — slow for thousands of tiles; chunk buffer must be explicitly remembered and set No visual tile overview; harder to identify corrupt or outlier-density tiles before the run starts

Stage 2 — Ground Classification (if missing)

  • lidR
  • lasR
has_ground <- function(las) any(las@data$Classification == LASGROUND)

classify_ground_csf <- function(las) {
  if (!has_ground(las)) {
    las <- classify_ground(
      las,
      csf(sloop_smooth    = TRUE,
          class_threshold = 0.5,
          cloth_resolution = 0.5,
          time_step       = 0.65)
    )
  }
  return(las)
}

# Apply across the catalog
opt_output_files(ctg) <- paste0(tempdir(), "/{*}_ground")
ctg_ground <- catalog_apply(ctg, classify_ground_csf)
# lasR does not support conditional per-tile logic inside the pipeline,
# so CSF runs unconditionally (safe — re-classifying already-labelled
# ground points does not change them if class_threshold is strict).

ground_stage <- classify_ground(
  csf(sloop_smooth     = TRUE,
      class_threshold  = 0.5,
      cloth_resolution = 0.5,
      time_step        = 0.65)
)
NoteStage 2 — Pros & Cons
lidR lasR
Pros Conditional logic (has_ground) avoids re-running CSF on pre-classified 3DEP tiles, saving time; can visualize classified ground on a single tile before batch-running CSF stage is compiled C++ — significantly faster per tile; seamless integration into the rest of the pipeline
Cons catalog_apply() with a custom function is verbose; per-tile conditional adds bookkeeping; R-level loop overhead No conditional: CSF always runs, adding unnecessary compute for 3DEP data where ground is already classified; cannot inspect one tile interactively before committing to the full run

Note: 3DEP data almost always ships with Class 2 pre-labelled. CSF is a safety fallback. CSF works by simulating a cloth dropped onto an inverted point cloud — points within class_threshold metres of the settled cloth are labelled ground.

Stage 3 — Height Normalization

  • lidR
  • lasR
normalize_and_save <- function(las) {
  # Build DTM from ground points via k-NN inverse distance weighting
  dtm <- rasterize_terrain(las, res = 1, algorithm = knnidw(k = 10, p = 2))

  # Normalize: subtract DTM → Z now = height above ground
  las <- normalize_height(las, dtm)

  # Save height as a named extra-bytes attribute BEFORE restoring raw Z
  las <- add_lasattribute(las, las@data$Z, "Height", "Height above ground (m)")

  # Restore raw Z (both raw elevation and Height now co-exist as attributes)
  las <- unnormalize_height(las)

  # Remove normalization artifacts and extreme outliers
  las <- filter_poi(las, Height > -0.5 & Height < 80)

  return(las)
}

opt_output_files(ctg) <- paste0(tempdir(), "/{*}_norm")
ctg_norm <- catalog_apply(ctg_ground, normalize_and_save)
# lasR's normalize() stage builds the DTM and subtracts it in one streaming pass.
# Z is modified in place (normalized height replaces raw Z in the output file).
# To preserve raw Z alongside height, use store_in_VPC() or a two-pass approach.

norm_stage <- normalize(knnidw(k = 10, p = 2))

# Height filter: use a filter stage after normalization
filt_stage <- filter_poi(
  keep_z_above(-0.5) & keep_z_below(80)
)

# Note: lasR normalizes Z permanently in the output LAS.
# If you need both raw Z and Height as co-existing attributes,
# run a separate first pass to save raw Z as extra bytes,
# then normalize in the second pass:

save_raw_z <- add_extrabytes("float", "RawZ", "Raw elevation (m above sea level)")
# ... then run normalize_stage in a chained pipeline
NoteStage 3 — Pros & Cons
lidR lasR
Pros add_lasattribute() + unnormalize_height() elegantly preserves both raw Z and normalized height in the same file — no second pass needed; DTM can be inspected as a raster object before committing DTM building and height subtraction happen in a single streaming pass without materialising the full raster in memory; much faster on very large tiles
Cons rasterize_terrain() builds a full DTM raster in memory before normalization — memory-intensive for large tiles with dense ground returns; R-level unnormalize_height() adds a linear scan overhead Z is overwritten in place — recovering raw elevation requires either a pre-saved copy or an extra-bytes pass; filter stage syntax differs from lidR’s filter_poi()

The height filter thresholds:

Filter Removes
Height > −0.5 m Sub-ground artifacts from DTM interpolation
Height < 80 m High noise, birds, aircraft

Stage 4 — Statistical Outlier Removal (SOR)

  • lidR
  • lasR
remove_noise_sor <- function(las) {
  # Classify noise — does NOT remove yet, only labels (Class 18)
  las <- classify_noise(las, sor(k = 15, m = 3))
  # Remove classified noise points
  las <- filter_poi(las, Classification != LASNOISE)
  return(las)
}

# Buffer must already be set on ctg (opt_chunk_buffer = 10)
opt_output_files(ctg) <- paste0(tempdir(), "/{*}_clean")
ctg_clean <- catalog_apply(ctg_norm, remove_noise_sor)
# lasR runs SOR natively in C++ with the buffer passed to exec().
# It classifies and removes in one stage.

sor_stage <- classify_noise(sor(k = 15, m = 3))
# Buffer = 10 m is set in exec() — applies to all neighborhood stages
NoteStage 4 — Pros & Cons
lidR lasR
Pros Two-step classify-then-filter gives you control: you can inspect flagged points before removing them (filter_poi(las, Classification == LASNOISE) → visualize); easy to tune k and m interactively on one tile SOR runs in C++ with multi-threading — 4–8× faster; buffer management is automatic in exec(); no separate filter step needed
Cons Pure R kNN search is slow for high-density tiles (> 50 pts/m²); chunk buffer must be remembered and set on the catalog separately; two function calls where one would suffice Cannot inspect flagged-but-not-yet-removed points without a debug run; slightly less fine-grained control over the classify/remove separation

Ordering rule (both packages): SOR must run after normalization (so height context is valid) and before decimation (so artificial sparsity does not mislead the neighbourhood statistics).

SOR formula:

\[\bar{d}_i = \frac{1}{k}\sum_{j \in \mathcal{N}_k(i)} \|p_i - p_j\|, \qquad \text{flag if } \bar{d}_i > \mu + m\sigma\]

k m Recommended setting
15 4–5 Sparse terrain / open canopy
15 3 Standard forest environments
8 2 Dense urban / noisy sensor

Stage 5 — Voxel Decimation (optional, recommended for 3DEP)

  • lidR
  • lasR
decimate_catalog <- function(las, min_dens = 5) {
  # Voxel edge length from target density
  voxel_res <- 1 / sqrt(min_dens)
  voxel_res <- min(voxel_res, 1 / sqrt(5))  # floor at 5 pts/m²
  las <- decimate_points(las, voxel(voxel_res))
  return(las)
}

opt_output_files(ctg) <- paste0(tempdir(), "/{*}_decim")
ctg_final <- catalog_apply(ctg_clean, decimate_catalog)
# lasR uses sampling_voxel() with the voxel edge length directly.
# Same formula: res = 1 / sqrt(target_density)

voxel_res   <- 1 / sqrt(5)          # 0.447 m for 5 pts/m² floor
decim_stage <- sampling_voxel(voxel_res)

# Other options in lasR:
# sampling_random(density = 10)         # random thinning
# sampling_homogenize(density = 10, res = 5)  # 2D homogenize
NoteStage 5 — Pros & Cons
lidR lasR
Pros Four decimation algorithms (voxel, random, homogenize, highest/lowest) — easy to swap and compare; result is immediately accessible as a LAS object for inspection sampling_voxel() runs in C++ — faster; chained directly after SOR with no intermediate file write required; cleaner syntax
Cons decimate_points() in a catalog_apply() loop has R-level overhead; limited to what lidR implements Fewer built-in algorithms than lidR (no highest/lowest equivalent in lasR at time of writing); no interactive mid-pipeline density check

See Section 1 below for a full comparison of all decimation algorithms.

Complete Pipeline Summary

  • lidR (full pipeline)
  • lasR (full pipeline)
library(lidR)

# ── 1. Setup ────────────────────────────────────────────
ctg <- readLAScatalog("path/to/las_folder/")
opt_filter(ctg)       <- "-drop_class 7 18"
opt_chunk_buffer(ctg) <- 10
opt_chunk_size(ctg)   <- 500

# ── 2. Ground classification ─────────────────────────
has_ground <- function(las) any(las@data$Classification == LASGROUND)
full_pipeline <- function(las) {
  # Stage 2: ground (if absent)
  if (!has_ground(las))
    las <- classify_ground(las, csf(sloop_smooth = TRUE,
                                    class_threshold = 0.5,
                                    cloth_resolution = 0.5))
  # Stage 3: normalize + save Height attribute
  dtm <- rasterize_terrain(las, res = 1, algorithm = knnidw(k = 10, p = 2))
  las <- normalize_height(las, dtm)
  las <- add_lasattribute(las, las@data$Z, "Height", "Height above ground (m)")
  las <- unnormalize_height(las)
  las <- filter_poi(las, Height > -0.5 & Height < 80)

  # Stage 4: SOR noise removal
  las <- classify_noise(las, sor(k = 15, m = 3))
  las <- filter_poi(las, Classification != LASNOISE)

  # Stage 5: voxel decimation
  las <- decimate_points(las, voxel(1 / sqrt(5)))

  return(las)
}

opt_output_files(ctg) <- "output/{*}_clean.laz"
output <- catalog_apply(ctg, full_pipeline)
library(lasR)

pipeline <-
  reader_las(filter = "-drop_class 7 18")        +  # Stage 1
  classify_ground(csf(sloop_smooth    = TRUE,        # Stage 2
                      class_threshold = 0.5,
                      cloth_resolution = 0.5))    +
  normalize(knnidw(k = 10, p = 2))               +  # Stage 3
  filter_poi(keep_z_above(-0.5) &
             keep_z_below(80))                   +  # Stage 3 filter
  classify_noise(sor(k = 15, m = 3))             +  # Stage 4
  sampling_voxel(1 / sqrt(5))                    +  # Stage 5
  write_las(ofile = "output/*.laz")                 # output

exec(pipeline,
     on     = "path/to/las_folder/",
     ncores = 4L,
     chunk  = 500,
     buffer = 10)
Important

When to choose which:

  • lidR — exploring a new dataset, tuning parameters interactively, datasets < 50 GB, need add_lasattribute() / unnormalize_height() to preserve both raw Z and height.
  • lasR — production runs, datasets > 50 GB, HPC clusters, time-critical workflows. Expect 5–10× speedup over equivalent lidR pipelines.

Section 1 — Decimation Methods in Depth

Decimation reduces point density to a target level. The choice of algorithm matters — different methods preserve different spatial and structural properties.

1.1 Random Thinning

  • lidR
  • lasR
las_random <- decimate_points(las, random(density = 10))
decim <- sampling_random(density = 10)

Each point is independently retained with probability \(p = d_{\text{target}} / d_{\text{local}}\). Spatially blind — does not consider where a point sits relative to its neighbours.

Strengths: fastest; preserves attribute distributions (intensity, return number); no spatial discretisation.

Weaknesses: no spatial uniformity — dense clusters stay dense; sensitive to random seed; density gradients persist in mixed 3DEP tiles.

Best use: quick exploration where spatial uniformity is not required.

1.2 Voxel Thinning

  • lidR
  • lasR
las_voxel <- decimate_points(las, voxel(res = 0.45))
decim <- sampling_voxel(res = 0.45)

3D space is divided into cubic voxels of edge res. One random point is retained per occupied voxel.

Strengths: enforces 3D spatial uniformity; removes density gradients from scan-angle overlap or multi-pass acquisition; consistent spacing benefits rasterisation and metric computation.

Weaknesses: retained point is random within the voxel — fine-scale vertical structure may be degraded; does not target a specific pts/m².

Best use: mixed 3DEP acquisitions; wall-to-wall AGB modelling.

1.3 Homogenize Thinning

  • lidR
  • lasR
las_homo <- decimate_points(las, homogenize(density = 10, res = 5))
decim <- sampling_homogenize(density = 10, res = 5)

2D cells of edge res are randomly thinned to exactly density pts/m². Cells already below target are left untouched.

Strengths: explicitly targets pts/m²; removes horizontal density gradients; preserves full vertical structure within each cell.

Weaknesses: 3D clustering can persist vertically; slower than random.

Best use: plot-level or pixel-level AGB regression where horizontal uniformity matters more than 3D structure.

1.4 Highest / Lowest Point per Cell

  • lidR
  • lasR
las_high <- decimate_points(las, highest(res = 1))
las_low  <- decimate_points(las, lowest(res = 1))
# Not a named stage in lasR; approximate with:
# filter to highest Z per voxel column using a custom step

Retains only the highest or lowest point per 2D cell. Not a general pre-processing step.

Method Retained points Application
highest Top-of-canopy Approximate CHM
lowest Near-ground Bare-earth approximation

1.5 Comparison Summary

Method Spatial uniformity Vertical structure Targets density? Speed lidR lasR
Random None Preserved Approximately ★★★★★ ✓ ✓
Voxel 3D uniform Partially lost No (size-based) ★★★★☆ ✓ ✓
Homogenize 2D uniform Preserved Yes (pts/m²) ★★★☆☆ ✓ ✓
Highest / Lowest 2D uniform No No ★★★★☆ ✓ Partial
Tip

For 3DEP with mixed acquisition years: voxel. For NEON AOP (single campaign, uniform density): no decimation needed. For plot-level regression: homogenize preserves vertical profile shape better.

Section 2 — Noise and Outlier Removal Methods

2.1 Class-Based Filtering

  • lidR
  • lasR
las <- filter_poi(las, Classification != LASNOISE)
# Or at catalog level:
opt_filter(ctg) <- "-drop_class 7 18"
# Pass filter string directly to reader_las():
read_stage <- reader_las(filter = "-drop_class 7 18")

Removes LAS Class 7 (low noise) and Class 18 (high noise) pre-labelled by the data provider. Zero computation cost. Always apply first.

lidR lasR
Pros Can apply at catalog level (no per-tile code) Integrated into the reader — no extra stage
Cons Easy to forget to set opt_filter before running Filter string syntax is the same; no additional control

2.2 Height-Based Thresholding

  • lidR
  • lasR
las <- filter_poi(las, Height > -0.5 & Height < 80)
filt <- filter_poi(keep_z_above(-0.5) & keep_z_below(80))
# Note: in lasR this filters on Z (normalized), not a separate 'Height' attribute

Fast, tunable, always complementary to SOR. Does not catch noise within the valid height range.

lidR lasR
Pros Filters on named Height attribute (works even after unnormalization restores raw Z) Direct filter stage; no attribute dependency
Cons Requires Height attribute to be present Filters on Z; if Z is raw elevation (not normalized), filter must use absolute elevation values instead

2.3 Statistical Outlier Removal (SOR)

  • lidR
  • lasR
las <- classify_noise(las, sor(k = 15, m = 3))
las <- filter_poi(las, Classification != LASNOISE)
sor_stage <- classify_noise(sor(k = 15, m = 3))
# Buffer is set via exec(..., buffer = 10)

\[\bar{d}_i > \mu + m\sigma \Rightarrow \text{noise}\]

lidR lasR
Pros Two-step classify-then-remove: inspect flagged points before deletion; easy to tune on one tile C++ multi-threaded kNN: 4–8× faster; buffer handled automatically in exec()
Cons Slow R kNN on dense clouds; buffer must be remembered separately Cannot inspect flagged points mid-pipeline without a debug run

2.4 Isolated Voxel Removal (IVR)

No native lasR equivalent. In lidR, requires a custom voxel_metrics() implementation. Faster than SOR on very dense clouds but resolution-dependent and less adaptive.

2.5 Isolation Forest (ML-Based)

No native implementation in either package. Requires Python via reticulate. Multi-attribute aware (intensity, return number) but 100× slower than SOR. Best used as a post-hoc validation of SOR results, not as a primary noise filter.

Important

Recommended stack for 3DEP data (both lidR and lasR):

  1. Class filter (-drop_class 7 18) — always first
  2. Height threshold (> -0.5 m and < 80 m) — after normalization
  3. SOR (k = 15, m = 3, buffer = 10 m) — after normalization, before decimation
